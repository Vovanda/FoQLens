**Необходима ли языковой модели фиксированная точность для любых вопросов?**

FoQLens поднимает точность весов только там, где это нужно вопросу.

**[vovanda.github.io/FoQLens](https://vovanda.github.io/FoQLens/)** - идея с ручками регулятора, которые
можно двигать: базовая точность, размер и сила зон, как складываются перекрытия и во что настройка
обходится в битах на вес. Метафора, на которую они действуют, нарисована на настоящих весах: карта
Gemma 4 E2B, 14 708 блоков, блоки, которые загораются вместе, лежат рядом.
[Документы](https://vovanda.github.io/FoQLens/docs.html) - механизм, предрегистрация и
каждый прогон - на том же сайте.

Большая цель - универсальный **регулятор точности**: один механизм, который задаёт, насколько тонко модель работает прямо сейчас, и делает её адаптивной - к задаче, к машине, на которой она запущена, и к ценности запроса ([идея](https://sawking.tech/blog/kvantovaniie-vsio-chto-vam-nuzhno)). Один набор весов обслуживает любое устройство и любую нагрузку: скупо работает на телефоне или на горячем загруженном сервере и открывается до полной точности ровно там, где это нужно запросу. Под давлением деградирует плавно - сначала грубеет фон, а то, что нужно запросу, остаётся резким.

Mixture of Experts - его жёсткий частный случай: эксперты с жёсткими краями, заданными при обучении, которые открывает роутер. Регулятор делает экспертов непрерывными - зоны возникают из самого запроса, родственные темы делят их, а стык двух тем заостряется, вместо того чтобы проваливаться между двумя экспертами.

**Главная гипотеза:** на трудном вопросе первый проход даёт черновик, большей частью прочитанный на базовой точности - приблизительную догадку, и она полезнее отказа, потому что догадку можно уточнить. Черновик возвращается во вход вместе с уточнением; зоны следующего шага ложатся точнее, и веса вне их влияют на ответ меньше. Поэтому там, где есть итерации - агент или рассуждение модели, - модель должна закончить лучше той же модели в исходной точности. Проверяется, когда появится модель FoQLens: агент на трудной многошаговой задаче, такой как проектирование программной архитектуры ([H4](docs/hypotheses.ru.md)). Дальше - горизонт: сеть, обученная с зонированием и читаемая тем же способом, должна обойти Mixture of Experts, обученную классически на тех же данных, не держа в памяти больше ни в какой момент ([H5](docs/hypotheses.ru.md)).

**FoQLens** (Focus + Quantization + Lens) - модель, которая использует этот регулятор. Её механизм - **FoQZones**, фокусируемые зоны квантования: точность весов распределяется по смыслу запроса, а линза - его метафора. Этот репозиторий - R&D внутри FoQLens, стенд, который проверяет ядро идеи: держать веса, важные для *этого конкретного запроса*, в высокой точности, а остальное читать грубо - и пусть модель сама скажет, какие это веса ([цели](docs/goals.ru.md)).

## Проблема

Квантование делает модели меньше и быстрее, храня веса меньшим числом бит. Каждая существующая схема - статическая или динамическая - решает точность по **фиксированной единице**: вся модель, слой, канал, токен, эксперт MoE. Границы задаёт архитектура; контроллер выбирает только, сколько бит получит каждая единица.

Вопросу про биологию и вопросу про доказательство нужна не *больше или меньше* точности. Им нужна точность **в разных местах**.

## Идея

1. Оценить каждый блок весов (64 выходные строки) по тому, насколько он важен для запроса - по собственным активациям и градиентам модели, без обученного роутера.
2. Вырастить **экспертные зоны** запроса из пиков этой оценки по расстоянию между блоками. Какая оценка, какое расстояние и как растут зоны - стратегии, которые ещё предстоит проверить ([docs/zone-strategies.ru.md](docs/zone-strategies.ru.md)).
3. Читать всю сеть на **базовой точности**, а каждую экспертную зону - точнее: резче всего в центре, со спадом к краю.

Три ручки, каждая делает одно:

- **базовая точность** (`floor` в скриптах) - точность всего, что вне зон, вплоть до полного отсутствия;
- **focus_area** - размер зон;
- **focus_strength** - насколько центры зон поднимаются над базой.

Память - результат настроек, бюджет не задаётся заранее: запрос, которому нужно мало, получает маленькие зоны и платит мало. Механизм в формулах, единственный источник правды по нему: [docs/quantization-filter.md](docs/quantization-filter.md).

Если идея верна, **экспертные зоны возникают** как области, которые остаются резкими, когда всё вокруг огрублено, - и родственные темы делят часть своей зоны, вместо того чтобы платить за неё дважды, как эксперты MoE.

## Куда это ведёт

- **Модели на устройстве.** Один файл весов для телефона, очков или ноутбука: точность следует батарее, нагреву и свободной памяти, а зоны остаются там, где запрос.
- **Цена запроса в дата-центрах.** Простой вопрос получает маленькие зоны и стоит мало; трудный - шире. Цена токена следует вопросу.
- **Агенты и рассуждение.** Везде, где черновик уточняется шаг за шагом - главная гипотеза выше.
- **Плавная деградация.** Под нагрузкой или при нагреве модель грубеет сначала в том, что запросу не нужно.

Это направления, которые открывает регулятор; каждое проверяется шагом [плана](docs/goals.ru.md), прежде чем о нём заявлено.

## Что проверяет стенд

Шаги, пронумерованные как в [предрегистрации](prereg/PREREGISTRATION.ru.md), упорядочены так, что каждый может убить следующий; где стоит каждый - в [дорожной карте](docs/goals.ru.md):

| Шаг | Вопрос | Убивает идею, если |
| --- | --- | --- |
| 0 | Разделяются ли темы в представлениях модели вообще? | не разделяются (тогда слаба модель) |
| 1 | Похожи ли поблочные маски внутри темы и различны ли между темами? Сконцентрированы ли они? | маски одинаковы для любого запроса |
| 2 | Делят ли родственные темы (биология-химия) больше своих зон, чем неродственные (биология-математика)? | структуры перекрытий нет |
| 2+ | Геометрия: аддитивны ли маски, есть ли зона стыка, ломает ли её абляция только смешанные вопросы? | - (уточняющий, не несущий) |
| 3 | Сколько из того, что знает модель, сохраняют зоны запроса против ровного квантования при той же памяти? Зоны другой темы и общая важность проверяют адрес | зоны сохраняют не больше ровного квантования при той же памяти |
| 7 | В агентной цепочке черновика и уточнений заканчивает ли зонная модель лучше той же модели в исходной точности и ровного квантования при той же памяти? (главная гипотеза, когда модель появится) | - |

Все предсказания были [предрегистрированы](prereg/PREREGISTRATION.ru.md) в git до каждого прогона, как направления («A > B»). Полные рассуждения - в [`docs/`](docs/).

## Статус

**Стенд и данные готовы; гипотезы проверяются со следующего шага.**

**Корпус того, что модель знает, построен и заморожен:** полная модель ответила своими словами на каждый вопрос шести
датасетов, нигде без вариантов, и вопрос остаётся, если ответ верен; в нём три
режима - ответ в тексте, только в весах, в двух текстах через шаг. В корпусе
20 640 вопросов: 18 576 модель знает, 2 064 не знает
([docs/corpus.ru.md](docs/corpus.ru.md)).

**Измерено, как модель держит знания при ровном квантовании:** D8 сохраняет 98.8% того, что знает полная
модель, D6 96.8%, D4 91.0%, D2 51.4%. Знания уходят сначала из весов: при ответе в тексте
D4 теряет 2.5%, при ответе только в весах - 13.0%. Это база для каждого теста
фильтра ([E002](experiments/E002-base-precision-d2/results.ru.md)). На первом замере наивное округление
давало на D2 бессвязные ответы ([E001](experiments/E001-uniform-quantization/results.ru.md)); после смены способа
квантования на k-quant базовая точность D2 держит половину знаний, и фильтр испытывается от D2.

**Предпосылка главной гипотезы проявилась сама.** На вопросах, которых полная модель не знает,
огрублённая модель отвечает там, где точная отказывается: в E001 на HotpotQA bf16 говорит, что в текстах ответа нет, в 12.1%
из них, D4 - в 4.6%, а принятые ответы растут с 13.4% до 25.2%. Огрубление снимает осторожность, новых знаний
оно не добавляет, и догадка иногда верна. На этом стоит [H4](docs/hypotheses.ru.md): черновую догадку можно
уточнить, «не знаю» - нельзя. Это проявилось на данных, не собранных, чтобы это показать; класс задач, который показывает это
намеренно, - отдельный эксперимент.

**Дальше - фильтр:** маска, которую спрашивают об ответе модели, и зоны, построенные из неё.

**Вопрос, которому служит всё это:** работает ли регулятор - структура там, где хватает грубого чтения,
детали там, где нужна резкость, выигрыш на итерациях. Экономия памяти - вторичная цель, план Б: даже без
выигрыша в качестве механизм экономит память при той же пригодности.

**Инженерия:** одна хранимая копия весов, читаемая на 2 / 4 / 6 / 8 битах: база k-quant (Q2_K, у чувствительных
классов Q4_K) и двухбитные уточнения поверх неё, по MoBiQuant с отступлениями
([E002](experiments/E002-base-precision-d2/results.ru.md)). Верхняя ступень зон - D8; файл модели может хранить и
хвост до исходных весов любого типа, так что модель читается до исходника бит в бит без чекпоинта
([docs/refocustensors.ru.md](docs/refocustensors.ru.md)). Раскладку глубин читает CUDA-ядро на тензорных ядрах прямо
из байтов копии, каждый блок строк до своей глубины: шаг декодирования E2B-it на смешанной раскладке при батче 32
занимает 28.8 мс против 422.6 с распаковкой и 20.4 у bf16 ([docs/kernels.ru.md](docs/kernels.ru.md)); префилл
распаковывает копию для GEMM.

## Воспроизвести

Требования: GPU NVIDIA с 16 ГБ+ памяти, [uv](https://docs.astral.sh/uv/). uv сам скачивает Python 3.12.

```sh
git clone https://github.com/Vovanda/FoQLens.git
cd FoQLens
uv sync                                              # torch (CUDA 12.8), transformers, bitsandbytes
uv run python scripts/download_models.py e2b e2b-it   # Gemma 4 E2B и E2B-it на закреплённых ревизиях, ~20 ГБ
uv run python scripts/cut_model.py e2b-it            # модель стенда: E2B-it в .refocustensors, ~9.3 ГБ
uv run pytest                                        # юнит-тесты + тесты здоровья стенда на GPU
```

Прогон по умолчанию занимает 0.8 GPU - эту долю VRAM и паузы между батчами, - чтобы карта оставалась пригодной; `--gpu-share 1` или `FOQLENS_GPU_SHARE=1` дают полную скорость.

Веса моделей в репозитории не хранятся. `scripts/download_models.py` скачивает их с Hugging Face (Apache 2.0, токен не нужен) на коммитах, закреплённых в `foqlens.model.REVISIONS`, и `foqlens.model.load()` читает ровно эти коммиты. `scripts/cut_model.py` режет скачанную модель в её папку [.refocustensors](docs/refocustensors.ru.md) вне репозитория, и стенд работает из этой папки. Добавьте `e4b` к скачиванию для модели подтверждения (~16 ГБ).

## Порядок работы

Предрегистрация → код прогона → прогоны → итоги, каждое в своём коммите, чтобы история показывала, что предсказания были раньше данных. Анализ слепой: сначала все прогоны, потом всё открывается разом. Единственное исключение - шаг 0, проверка, что модель вообще годна для стенда.
