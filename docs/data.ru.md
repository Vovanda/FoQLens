# Данные прогонов: файлы и DuckDB поверх них

**Принцип.** Всё, что пишет стенд, - ответы модели, вердикты судей, чтения Claude - лежит в файлах JSON
Lines: строка на ответ, файл на корпус и уровень. Файлы - источник правды. Прогон только дописывает в них,
и строки стоят в том порядке, в каком их написала модель. Базы данных в репозитории нет - только движок
запросов, который читает файлы там, где они лежат, и ничего не хранит.

**Раны судьи.** Вердикт не пишется поверх ответа, который он читает. Каждый проход судьи по одному файлу
ответов - отдельный ран, `judge/<level>/<corpus>/<run>.jsonl`, названный по времени старта, со сводкой
рядом: коммит кода, прочитанный файл, выбранные строки и отсуженные вопросы. Следующий ран переспрашивает
только то, что ему дали - например, N/A прежнего рана, - и прежний ран остаётся. Вердикт по вопросу берётся
из последнего рана, который его читал: представление `verdicts` поверх представления `judged` со всеми ранами.

**Почему не база данных.**

- Упавший прогон дописывает с места остановки и пропускает уже записанные ответы; транзакции ему не нужны.
- Слепой анализ и улики - обычные папки: сломанный прогон убирается в сторону одной командой и хранится
  как улика.
- Git видит данные: прогон коммитится как есть, его diff можно прочитать.
- Порядок строк - тоже данные: строка помнит батч, в котором её написали. У таблицы базы порядка нет.

**Почему DuckDB.** Мы его выбрали и рекомендуем для такой работы:

- он читает JSON Lines там, где они лежат - glob по папкам, схема выводится сама, старые и новые строки с
  разными полями читаются вместе; второй копии данных, которая разойдётся с файлами, нет;
- он встроенный - пакет в окружении, без сервера;
- это колоночный движок для аналитики: агрегаты по десяткам тысяч ответов - секунды;
- его SQL - диалект PostgreSQL (DuckDB взял его парсер) с удобствами сверху: `GROUP BY ALL`, `QUALIFY`,
  `PIVOT`, функции над списками, регулярные выражения с классами письменности Unicode;
- результаты отдаются в pandas или Polars как есть.

ClickHouse отвергнут (сервер, и не этот масштаб), SQLite тоже (строчный, и файлы пришлось бы грузить в
таблицы). Движок заменим: Polars, pandas и ClickHouse local читают те же файлы. Запросы лежат в одном модуле,
[`foqlens.runs`](../src/foqlens/runs.py); остальной стенд просит срез и SQL не знает.

**Что это дало в первый вечер.**

- Срезы этапа 1 равны тому, что записал его отбор, `passed-bf16.json` - согласие точного совпадения и судьи
  с чтениями Claude по корпусам (`tests/test_runs_unit.py`).
- Весь E016 - удержание знаний по уровням и корпусам, согласие судей, темы, хрупкость, язык ответа -
  считается за секунды.
- Срез «потерянные ответы рядом с ответами bf16» показал китайские иероглифы, а порядок строк показал, что
  ломались целые батчи. Так нашлась неисправность стенда
  ([#14](https://github.com/Vovanda/FoQLens/issues/14)): слитное ядро внимания схлопывало батчи с паддингом.
