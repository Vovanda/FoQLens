# Формат модели .refocustensors

Модель хранится одной стопкой уточнений: из одного файла читается любая глубина, от грубой базы до верха, на котором модель нарезана, и ничего не хранится дважды. Файл, нарезанный целиком, кончается хвостом `exact` и возвращает исходные веса бит в бит, в их собственном типе - bf16, fp16 или fp32. Поэтому папка с файлом `.refocustensors` работает без чекпоинта Hugging Face, в каком бы типе ни вышла модель.

## Стопка

Каждая управляемая матрица весов хранится стопкой. Внизу база, выше уточнения, каждое уточняет всё, что под ним. Глубина считается в 2-битных ступенях.

| Слой | Бит на вес | Прочитано до него | Уровень |
| --- | --- | --- | --- |
| база Q2_K | 2.625 | база | D2 |
| уточнение 1 | 2 | + уточнение 1 | D4 |
| уточнение 2 | 2 | + уточнение 2 | D6 |
| уточнение 3 | 2 | + уточнение 3 | D8 |
| `exact` | 6.5 (3.8 под энтропийным кодером) | всё | исходник бит в бит |

Пример: матрица 2×256 bf16, первый вес строки 0.

```
исходный вес                     -0.001534
D2  база                         -0.008173
D4  + уточнение 1                +0.000138
D6  + уточнение 2                -0.001940
D8  + уточнение 3                -0.001421
exact: округлить D8 до bf16 и сдвинуть на -15 соседних значений bf16  ->  -0.001534
```

## Резка

Исходник - самая точная версия модели, какая есть; из него нарезается всё.

База - k-quant из llama.cpp: Q2_K, а у чувствительных классов (`k_proj`, `v_proj`, `o_proj`, `down_proj` и модули per-layer) Q4_K. Их база занимает две ступени, поэтому D2 у них читается как D4. Уточнение k хранит 2-битный код поправки с шагом `шаг блока базы / 4^k`, своей шкалы у него нет. `exact` хранит, на сколько ulp исходного типа сдвинуть предсказание - вес, прочитанный до последнего уточнения и округлённый до исходного типа.

База и уточнения считаются в fp32. bf16, fp16 и fp32 переводятся в fp32 без потерь, поэтому резка одна для любого исходного типа. От типа зависит только `exact`: сдвиг считается в ulp этого типа.

Нижний край стопки - параметр, сейчас D2 (Q2_K). Уточнений может быть сколько угодно: `refinement.<k>` читаются по порядку, пока есть, и число в формат не зашито; сейчас их кладётся до D8.

Тензоры, которые регулятор не читает (эмбеддинги, нормы, башни зрения и звука), лежат в файле как в исходнике. У E2B-it это 6.04 из 9.54 ГиБ чекпоинта, из них 4.7 ГиБ - таблица эмбеддингов per-layer.

## Файл

Контейнер - safetensors: заголовок JSON и дальше сырые тензоры. Тензор читается по смещению из заголовка, без чтения остального и без отображения файла в память. Своё в формате - имена тензоров и метаданные. Для каждого управляемого веса `<ключ>` - его имени в исходнике:

| Тензор | Тип и форма | Что хранит |
| --- | --- | --- |
| `<ключ>.base` | uint8 [out, супер-блоки, байты] | база байтами блоков ggml `block_q2_K` / `block_q4_K` |
| `<ключ>.refinement.<k>` | uint8 [out, in / 4] | уточнение k, 4 кода по 2 бита в байте |
| `<ключ>.exact.widths` | uint8 [out, in / 16] | ширина сдвигов в каждой группе из 16 весов строки |
| `<ключ>.exact` | uint8 [байты] | сдвиги, группа за группой, строка за строкой |

База в байтах ggml занимает 2.625 и 4.5 бита на вес: это ровно коды, шкалы блоков и множители супер-блока. Тест сверяет эти байты с декодером gguf-py. Сдвиги `exact` переведены в неотрицательные числа (zigzag) и записаны в каждой группе шириной по самому большому из них. Байты блока строк идут подряд, поэтому блок зоны читается отдельно.

В метаданных файла: имя и версия формата, исходник с ревизией и для каждого управляемого веса формат базы, форма и исходный тип.

Предсказание, от которого считается `exact`, одинаково у всех, кто его читает. Тест сверяет его на CPU и на GPU бит в бит.

## Как получить

```
uv run python scripts/download_models.py e2b-it
uv run python scripts/cut_model.py e2b-it
```

Первая команда скачивает чекпоинт на закреплённой ревизии, вторая режет его в папку `~/.cache/foqlens/models/gemma-4-E2B-it@3e22461f/`: config, токенизатор и `model.refocustensors`. Переменная `FOQLENS_HOME` переносит эту папку. Веса в репозиторий не попадают.

`--depth D8` (или D2, D4, D6) обрезает стопку на этом уровне, без `exact`: файл E2B-it до D8 весит 7.92 ГиБ и ложится в соседнюю папку `...@3e22461f-D8/`, полная модель не затирается. Такой файл читается только резидентно.

## Загрузка

Стенд (`Bench.load`) берёт модель из трёх источников:

| Источник | Что читается | Уровни | GPU, E2B-it |
| --- | --- | --- | --- |
| `FILE`, по умолчанию | исходные веса из файла бит в бит, копия каждого модуля - из файла | bf16, D2 ... D8 | 8.6 ГиБ и копии по мере чтения |
| `RESIDENT` | только копии; исходные веса управляемых модулей не грузятся | D2 ... D8 | 7.06 ГиБ, из них 1.86 копии |
| `CHECKPOINT` | чекпоинт Hugging Face, копия квантуется из bf16 | bf16, D2 ... D8 | 8.6 ГиБ и копии |

Модель без нарезанной папки не загружается, и ошибка называет команду нарезки. Веса присваиваются параметрам модели без копии: пик выделенной памяти Windows (commit charge) при загрузке 13.5 ГиБ. Маски стенд считает на bf16, поэтому резидентный стенд подходит только для прогонов без масок. В резидентном режиме 4.7 ГиБ занимает таблица эмбеддингов per-layer в bf16; копии держат базу блоками ggml и уточнения упакованными, как в файле.

Все три источника дают одни и те же логиты бит в бит на каждой глубине, а `FILE` и `CHECKPOINT` ещё и на bf16 - так же, как `from_pretrained`.

## Размер

E2B-it: файл 9.34 ГиБ, чекпоинт bf16 9.54 ГиБ. Из них 6.04 ГиБ - тензоры, которые регулятор не читает и которые лежат как в исходнике.

Файл, обрезанный на уровне (`--depth`), и удержание знаний bf16 на замороженном корпусе (E002):

| Верх стопки | Управляемые веса, бит на вес | Управляемые веса, ГиБ | Файл, ГиБ | Удержание |
| --- | --- | --- | --- | --- |
| D2 | 3.33 | 0.73 | 6.77 | 51.4% |
| D4 | 4.57 | 1.00 | 7.04 | 91.0% |
| D6 | 6.57 | 1.44 | 7.48 | 96.8% |
| D8 | 8.57 | 1.88 | 7.92 | 98.8% |
| исходник bf16 (`exact`) | 15.05 | 3.30 | 9.34 | 100% |
| чекпоинт bf16 | 16 | 3.51 | 9.54 | 100% |
| GGUF UD-Q2_K_XL / Q4_K_M | - | - | 2.24 / 2.89 | 80.0% / 95.0% |

D8 и полный файл измерены нарезкой, D2-D6 сложены из размеров частей. GGUF квантуют и тензоры, которые регулятор не читает, поэтому их файлы меньше; управляемые веса у нас на D4 и D6 весят 1.00 и 1.44 ГиБ.

Управляемые веса (1.88 млрд), бит на вес: база и уточнения до D8 плюс хвост до bf16 при разном кодировании хвоста (`scripts/exact_tail_cost.py`):

| Кодирование хвоста | Всего бит на вес |
| --- | --- |
| ширина на группу из 256 весов | 20.13 |
| ширина на группу из 32 | 15.92 |
| ширина на группу из 16 - в файле | 15.05 |
| энтропийный кодер | 12.39 |
| энтропийный кодер с экспонентой предсказания как контекстом | 11.66 |
| сам bf16 без базы, энтропия | 10.55 |

Энтропийный кодер сократит файл ещё на ~0.6 ГиБ. Сумма почти не зависит от того, после какой глубины начинается хвост: 12.4 бита по энтропии после D4, D6 и D8. База однозначно вычисляется из исходника, и каждое уточнение снимает с хвоста около своих 2 бит.

## Секции и контрольные точки

Стопку можно резать на секции, каждая секция - свой файл. Файлы склеиваются в один и разрезаются обратно перекладкой тензоров, без пересчёта.

- Стопка всегда одна цепочка: одна база внизу, выше только уточнения.
- Дописать сверху (до bf16 или fp32) - добавить уточняющую секцию.
- Дописать снизу - перерезать: новая база и уточнения, прежняя база становится хвостом `exact` над ними и читается бит в бит.

Контрольная точка - уровень, через который стопка обязана пройти бит в бит: готовая модель, своя или чужая. Она стоит либо на границе наших уточнений, либо на формате, у которого есть шаг блока (Q2_K ... Q6_K, Q8_0): уточнения над ней берут этот шаг. У IQ-форматов шага блока нет, контрольной точкой они быть не могут.

Уровень, для которого нет скачанной секции, отклоняется, когда задаётся раскладка, - до вычислений.

| Исходник | Что нужно | Файлы | Бит на вес | Что для этого построить |
| --- | --- | --- | --- | --- |
| bf16 | стенд, зоны до D8, исходник для судьи | база ... D8, `exact` | 15.05 | построено |
| bf16 | стенд только на D2 ... D8, без исходника | база ... D8 | 8.57 | построено (`--depth D8`) |
| bf16 | маленькая модель, полная по запросу | база, D4 / D6, D8, `exact` | 4.6 / ~10.5 | секции |
| fp32 | зоны до fp32, bf16 как промежуточная точка | база ... D8, `exact` до bf16, `exact` до fp32 | не мерил | цепочка хвостов |
| fp32 | потолок 16 бит: модель читается самое большее до bf16 | база ... D8, `exact` до bf16; секция fp32 не скачивается | не мерил | цепочка хвостов |
| чужой Q8_0, других нет | базовая точность ниже 8 бит | база ... D6, `exact` до Q8_0 | ~8.5, не мерил | порт Q8_0, исходник с блочным квантованием |
| fp8 с блочными шкалами | то же | база ... D6, `exact` до fp8 | не мерил | исходник с блочным квантованием |

| только чужой Q2_K | запуск | база | 2.6 | ничего; выше D2 информации нет |

## Память под раскладку и ZERO

Цель - держать на GPU только то, что читает раскладка. Базовая точность D2 и зоны D8 на 10% блоков: 0.9 · 3.33 + 0.1 · 8.57 ≈ 3.9 бита на вес. При базовой точности ZERO вне зон ≈ 0.9 бита.

Сейчас ZERO экономит вычисления: для блока на ZERO ядро ничего не читает, его выход - нули ([ядро](kernels.ru.md)). Копия модуля при этом лежит в памяти целиком. Памяти ZERO даст, когда появятся две вещи: потолок глубины по блокам для копии k-quant (блок с потолком 0 ничего не хранит) и чтение из файла по блокам под раскладку, с догрузкой и выгрузкой при её смене. Файл к этому готов: строки блока в каждом тензоре лежат подряд, и тензор читается по смещению.

## Что есть сейчас

Построены база Q2_K / Q4_K по llama.cpp, уточнения до D8, хвост `exact` для bf16, fp16 и fp32, запись папки модели, обрезка на уровне и три источника загрузки стенда; раскладку глубин читает CUDA-ядро прямо из байтов копии ([ядро](kernels.ru.md)). Модель из файла совпадает с чекпоинтом бит в бит, копия каждого модуля - с копией, квантованной из bf16; лестница на корпусе совпадает с E002. Секции, дописывание снизу, чтение по блокам под раскладку, порты других форматов и исходник с блочным квантованием - после.
